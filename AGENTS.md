# Правила разработки «Корсик» — для людей и ИИ-агентов

Цель — первое место на защите 25.10. Каждое изменение должно **измеримо** приближать к ней: продукт работает, качество подтверждено цифрами, интерфейс понятен человеку без опыта. Эти правила обязательны для всех: людей, Claude Code, Codex, Cursor, Copilot и любых других агентов. Если правило мешает делу — обсудите в чате команды. Молча нарушать нельзя.

## 0. Перед первой задачей

1. Прочитайте `README.md` (что за продукт и как запустить), этот файл и `docs/research.md` (гипотезы и вопросы команды).
2. Запустите проект локально по README и убедитесь, что проверки зелёные (раздел 4).
3. Один раз включите хуки репозитория: `git config core.hooksPath .githooks`.
4. Возьмите задачу: issue в GitHub, назначенный на вас. Без задачи код не пишем.

## 1. Авторство

- Коммиты, PR, комментарии и ревью — от имени человека. `git config user.name` и `user.email` — ваши.
- **Запрещено** указывать ИИ-агента как автора где-либо: трейлеры `Co-Authored-By` с ИИ, строки «Generated with …», эмодзи-подписи 🤖, упоминания агента в коде, комментариях, названиях веток, PR и issue. Ботов и агентов в коллабораторы не добавляем.
- Claude Code: подпись отключена в `.claude/settings.json` (`"attribution": {"commit": "", "pr": ""}`) — не меняйте. Другие агенты: отключите подпись в их настройках или удаляйте её до коммита.
- Защита стоит дважды. Хук `.githooks/commit-msg` отклоняет такой коммит локально, CI проверяет сообщения коммитов в PR.
- **Единственное исключение** — раздел «Использование ИИ» в README и слайд в презентации. Их требует Положение хакатона (п. 4.3.3–4.3.4), без них решение могут не принять. Не удаляйте и не меняйте их без решения команды.

## 2. Git: только ветки и pull request

- В `main` напрямую не пушим — ни «мелочь», ни README. Всё идёт через PR.
- Ветка от свежего `main`: `feat/…`, `fix/…`, `ui/…`, `docs/…`, `eval/…`; имя — 2–4 слова латиницей через дефис (`feat/max-webhook-retry`).
- Одна задача — одна ветка — один PR. Дифф до ~400 строк кода; контент и сгенерированные файлы не считаются. Больше — делите на части.
- Коммиты атомарные, сообщение в повелительном наклонении по существу: «Добавить проверку чисел в ответе», а не «fix», «update», «wip».
- Перед PR: `git fetch origin && git rebase origin/main`. Конфликты решайте у себя, не в `main`.
- PR заполняется по шаблону: что, зачем, как проверено, цифры и скриншоты.
- Мерж — squash, только при зелёном CI и после ревью другого участника. Ревьюер проверяет по разделу 4, а не «на глаз».
- Никогда: force-push в `main`, коммит `.env`, токенов, моделей, баз данных, материалов кейса.

**Версии**
- Нумерация по [SemVer](https://semver.org/lang/ru/): `MAJOR.MINOR.PATCH`. Номер живёт в `backend/pyproject.toml`, `web/package.json` (одинаковый в обоих) и в git-тегах `vX.Y.Z`. В названии продукта номера нет: продукт называется «Корсик».
- До пилота у заказчика версии `0.x`. `MINOR` — новая возможность для пользователя, `PATCH` — только исправления.
- Релиз — отдельный PR, который поднимает номер в обоих файлах. После мержа на этот коммит `main` ставится тег `vX.Y.Z` и публикуется GitHub Release со списком изменений. Жюри сдаём релиз с тегом.

## 3. Кто что делает

Одна зона — один владелец. Работаете в своей зоне. Чужие файлы меняете только по договорённости в issue или PR владельца. Общие файлы (`backend/app/models.py`, `backend/app/config.py`, `web/src/api.ts`, `web/src/components/ui.tsx`) меняйте минимально и явно опишите это в PR.

| Зона | Что входит | Владелец |
|---|---|---|
| Бот и сценарий | `backend/app/bot/`, `backend/scenario/korsik.yaml` | — |
| Поиск по документам и качество | `backend/app/rag/`, `backend/eval/` | — |
| Аналитика и эскалации | `backend/app/analytics/`, `backend/app/bot/escalation.py` | — |
| Интерфейс | `web/` | — |
| MAX и развёртывание | `backend/app/channels/`, `docker-compose.yml`, `Dockerfile` | — |
| Защита: презентация, видео, тизер | `TEASER.md`, материалы вне кода | — |

Владельца вписывает команда; агент сам себя владельцем не назначает. Перед началом работы проверьте открытые PR — не делайте ту же задачу параллельно.

## 4. Готово = объективно лучше

PR вливается, только если выполнено всё, что относится к изменению. Вывод команд — в описании PR.

| Что меняли | Обязательная проверка |
|---|---|
| Любой backend | `cd backend && uv run ruff check . && uv run pytest -q` |
| Любой frontend | `cd web && bun run build` (собирает и проверяет типы) |
| Поиск, промпты, чанкинг, пороги, модели | `uv run python eval/run_eval.py --e2e` до и после, таблица в PR. Мерж без регрессии: Hit@1 и Hit@5 не ниже, ложных ответов на вопросы вне базы не больше, верных ответов не меньше. Улучшили одно и ухудшили другое — решает команда |
| Сценарий, диалог, опросы | Пройти демо-сценарий из README в демо-чате и описать, что проверено. Детерминированная логика — новый тест в `backend/tests/` |
| Интерфейс | Скриншоты до и после (1440×900), пустое состояние и состояние ошибки |
| Контент (тексты Корсика) | Предпросмотр на «ты» и на «вы»; тон — как в ТЗ |

Плюс всегда:
- **Нет новых багов.** Затронутые сценарии проверены руками. Найденный по пути баг — отдельной задачей, а не молча.
- **Нет мусора.** Отладочных `print`, закомментированного кода, неиспользуемых файлов и абстракций «на будущее» нет.
- **Стиль окружающего кода.** Новая логика повторяет соседний код: те же имена, плотность комментариев, подходы. Чужой модуль целиком не переписываем.

## 5. Цифры и факты — только проверяемые

Любое число в коде, интерфейсе, README, презентации и речи на защите должно иметь источник:

1. материалы кейса и ТЗ (например, «HR тратит до 40% времени» — цифра заказчика, так и подписываем);
2. наш замер с командой воспроизведения (eval, тест, лог);
3. внешний источник со ссылкой; данные вендоров помечаем как данные вендоров;
4. настройка с комментарием, почему выбрано такое значение. Пороги и гиперпараметры подбираются замером, не на глаз.

Запрещено: выдумывать метрики, экономию «N часов», отзывы, клиентов, результаты пилотов; выдавать демо-данные за реальные; округлять в свою пользу. Нет данных — так и пишем: «измерим на пилоте».

## 6. Интерфейс и тексты

Для кого делаем: HR-менеджер без технического опыта, руководитель, у которого нет времени, новичок на заводе с телефона.

- **Простой язык.** В интерфейсе нет слов RAG, NLP, чанк, эмбеддинг, score, id и английских терминов. Технические детали показываются только в «Режиме демонстрации».
- **Один экран — один ответ** на вопрос «что мне сделать сейчас?». Главное действие одно и заметно, второстепенное не кричит.
- **Пустые состояния** объясняют, что здесь появится и что сделать. Ошибки — человеческим языком и с выходом.
- **Единая система.** Компоненты — из `web/src/components/ui.tsx`, цвета и шрифты — токены из `web/src/index.css`. Новый общий элемент добавляется туда, а не копируется в страницу.
- **Красиво и современно, но не перегружено.** Воздух, выравнивание, понятная иерархия. Каждую новую деталь проверяем вопросом: что пользователь потеряет, если её убрать? Ничего — убираем.
- **Тексты Корсика** — дружелюбно и коротко, в стиле ТЗ, с вариантами `{ты|вы}` и `{name}`.
- **Приватность.** Руководитель не видит свободных ответов новичков и сигналов о себе — это проверяется на сервере, не только в интерфейсе.

## 7. Честность продукта

Первый критерий жюри — «соответствует ли фактическая функциональность заявленной». Поэтому:
- в README, презентации и речи — только то, что работает и показывается;
- планы явно помечены как дорожная карта;
- ограничения перечислены в README («Честно об ограничениях») — их не прячем, а держим актуальными.

## 8. Безопасность и Положение хакатона

- Материалы кейса (ПВТР, политики, ТЗ, презентация кейса) не коммитим и не загружаем в публичные ИИ-сервисы (п. 4.3.2). Локально они лежат в `materials/`, папка в `.gitignore`.
- Секреты — только в `.env` (не коммитится), пример — `.env.example`.
- Зависимости — только бесплатные и открытые (п. 4.1.6). Новая зависимость — с обоснованием в PR.

## 9. Отдельно для ИИ-агентов

- Сначала прочитайте код вокруг места правки и повторите его стиль. Делайте только то, что в задаче.
- Не угадывайте требования: не ясно — спросите человека в задаче.
- Не пишите «готово», пока не прошли проверки из раздела 4. Приложите их вывод.
- Не создавайте новых документов, отчётов и файлов-заметок, если задача этого не требует.
- Этот файл меняется только через PR с согласия команды.
